    Local Data Stack — Project Instructions

    Adopted as a spec node. This file is the project's governance rule set. It is
    read as-is, with one exception: where a gate has drifted from the code, the drift is
    called out inline under Drift as read against the tree at the bottom. Not yet
    reviewed by the owner — status: draft.

    Project Identity

    This is a local-first, agent-friendly analytics stack using Rill (BI-as-code)
    with DuckDB as the embedded OLAP engine. The project models K-12 education data
    with dbt and serves dashboards through Rill Developer / Rill Cloud.

    The dashboard layer is aligned with the California School Dashboard (CDE
    accountability system). Four state indicators are exposed: Chronic Absenteeism,
    Suspension Rate, Academic (ELA), and English Learner Progress (ELPI). Each
    carries the CDE-pre-computed Status, Change, and Performance Color (Red→Blue)
    straight from the CDE downloadable Dashboard data files.

    Core Philosophy

    BI-as-Code. Every dashboard, metric, and model is defined as YAML + SQL files
    in version control. Nothing is GUI-only. This makes the entire analytics stack
    readable by AI agents and auditable by humans.

    One metrics layer, many clients. Measures and dimensions are defined once in
    metrics views and consumed by dashboards, AI agents, SQL queries, and external
    MCP clients — all resolving the same governed definitions.

    Local-first, cloud-ready. Develop and verify everything locally with
    rill start. Deploy to Rill Cloud when ready. The same files work in both
    environments. DuckDB embedded locally; MotherDuck or Rill Cloud in production.

    Agent-friendly by design. YAML definitions, CLI tooling, and Metrics SQL
    make this stack naturally consumable by AI agents. Every resource is code an
    agent can read, reason about, and edit.

    Project Structure

    Development Constraints

    Gate 1: Declarative Only

    Everything in rill_project/ must be defined in YAML + SQL files.
    No adding dashboards, measures, or dimensions exclusively through the Rill UI.
    The UI is for preview and exploration; definitions live in code.

    Gate 2: Verify Locally First

    Before committing any change to rill_project/:

    Gate 3: No Duplicated Metrics

    Every metric is defined exactly once. If the same business concept
    appears in two places (e.g., status_value in two metrics views),
    one must delegate to the other via parent or requires. The four
    CDE Dashboard metrics views each own their indicator's Status/Change/Color
    columns — do not recompute these in a second view.

    Gate 4: Agent Queries Use Metrics SQL

    AI agents querying data must use Metrics SQL against metrics views,
    not raw SQL against underlying tables. This ensures governed, secure
    access through the metrics layer.

    Gate 5: Description on Every Resource

    Every dimension and measure must have a description field.
    AI agents cannot infer business meaning from column names alone.

    Gate 6: Deterministic Metrics

    Measures must use precise SQL expressions, not natural language
    descriptions as their only definition. Use ai_instructions for
    supplemental context, not as a substitute for SQL.

    Language & Format Standards

    • Dimension/measure names: snake_case (e.g., chronic_absence_rate)
    • Display names: Title Case (e.g., "Chronic Absence Rate")
    • File names: snake_case (e.g., chronic_absenteeism_risk.yaml)
    • Timeseries column: _loaded_at for batch-loaded data
    • OLAP dialect: DuckDB SQL (standard SQL functions + DuckDB extensions)

    Metrics SQL Constraints

    When writing queries against metrics views, follow these rules:

    • No JOINs across metrics views (one metrics view per query)

    • Always include LIMIT for agent-driven queries (default 100)

    Drivers

    Student-level data cannot leave the device; published indicators must not be second-guessed by ad-hoc SQL; and the same YAML files must work on a laptop and in a deployed Rill project. Every boundary below exists because of one of those three.

    Shape

    oss_framework/ owns ingestion and modeling (dlt pipelines + a dbt project). scripts/ orchestrates and exports. rill_project/ is BI-as-code over the exported tables. nl_query/ is the natural-language client. training/ produces the weights nl_query/ loads. lfed-app-architecture is the client that will absorb nl_query/ and the dashboards into one surface.

    Decisions

    Two query paths coexist by design. docs/PHASE4A_DATA_MODEL_DESIGN.md (lfed-docs-phase4a) keeps CDE staging tables directly queryable and a pre-joined mart_cde_school_accountability OBT for dashboard-shaped reads, so a question can be answered without joining twelve staging tables. Today the direct path is hidden from live schema introspection: main_staging is absent from DEFAULT_EXPOSED_SCHEMAS in nl_query/data_engine.py (which filters get_schema_info(), though validate_sql() does not enforce DEFAULT_EXPOSED_SCHEMAS at execution time) while nl_query/prompts.py still advertises main_staging.stg_cde__* tables in its static fallback schema and system prompt — recorded as unresolved in lfed-docs-phase4a. lfed-app-architecture narrows this: the governed path is a structured query against a metrics view, and raw warehouse SQL is the explicitly-marked fallback, chosen by the server rather than the model — which is what that doc's "future Phase 5 router" was reaching for.

    Privacy suppression lives in the models, not the clients. dbt enforces k≥5 (HAVING COUNT(...) >= 5) when building marts, and CDE exports carry their own is_suppressed ('*' marker) and is_small_n (n<11) flags. Consequence, and a trap for new clients: rows the warehouse dropped cannot be recovered downstream, and nothing in nl_query/ reports suppression at answer time — the app must surface both regimes rather than imply it applies them.

    The guard is a client-side invariant, not a warehouse capability. Read-only connections plus schema/table/column filtering: today get_schema_info() filters live introspection by schema allowlist (DEFAULT_EXPOSED_SCHEMAS), blocked privacy schemas (main_privacy_sensitive, anything matching priv_), blocked table patterns (^_dlt, pii_lookup), and column-level PII exclusions (PII_COLUMNS), while execution-time validate_sql() enforces forbidden write tokens, SELECT-only, blocked privacy schemas, and live EXPLAIN validation (with a 1000-row cap and 10-second default watchdog in execute_safe, overridden to 30 s by the Gradio app). Note that validate_sql() does not yet enforce DEFAULT_EXPOSED_SCHEMAS, _BLOCKED_TABLE_PATTERNS, or PII_COLUMNS at execution time — a gap to close before lfed-app-architecture exposes human-in-the-loop SQL editing. Any new client inherits and hardens this module rather than re-implementing it.

    Metrics views are the only definition of a governed indicator. Rill YAML is the source of truth for labels, measures, formats, and dimension descriptions, so a client that needs metric semantics reads that YAML instead of restating it — the reason the app fetches view metadata at runtime.

    Model identity is not an interface. nl_query/model_inference.py wraps transformers+PEFT behind a class shaped like llama_cpp.Llama specifically so the backend can be swapped; the app binds to a SQL-generation contract, not a checkpoint. See lfed-app-inference.

    Invariants

    • No cloud call in the data path. dlt, DuckDB, dbt, Rill, and the model all run locally; lfed-docs-instructions' "deploy to Rill Cloud when ready" is an option, never a requirement of the local path.
    • No Python-package imports between oss_framework/, nl_query/, and top-level scripts/; oss_framework/ and nl_query/ meet only through the DuckDB file. The single cross-module code load is oss_framework/cli.py's file-path exec of scripts/export_to_rill.py (dependency table above) — a checkout-only coupling, not an import edge.
    • The natural-language client opens the warehouse read-only. Nothing that a model generated may mutate it.
    • A dashboard number and a natural-language answer for the same indicator must not be able to disagree, because both resolve through the same metrics view. (lfed-docs-known-issues records that today they can.)
    • Governance rules are enforced where they can be: privacy joins stay in main_privacy_sensitive, which no client is allowlisted to see.

    Out of scope

    • Cross-module operational concerns — pipeline scheduling and CI contract tests — stay inside lfed-mod-pipeline-ops.
    • Superseded surfaces are recorded here once, and not re-listed in the module specs that contain them: schema/*.json holds legacy interactive-dashboard card specs — the files themselves are only parse-validated by scripts/contracts/contract_tests.py, but their SQL is duplicated into scripts/contracts/contract_query_manifest.json, which CI executes against the warehouse, so retiring the legacy main_analytics.v_* views breaks the contract-tests job; oss_framework/dbt/models/exports/rill_*.sql is a legacy export layer beside the current four rill_cde_* views; the repo-root test_rill_integration.py (five metrics views that do not exist in rill_project/metrics/) and test_uat.py (Dash apps on ports 8050–8054 that no longer exist) are archival candidates, while pyproject.toml's testpaths = ["oss_framework/tests", "."] still collects them on a bare pytest. docs/superpowers/ and hackathonDocs/ are history and input, not specs.
    • The unified app's process topology, envelope contract, and renderer catalog belong to lfed-app-architecture; this document describes only the seam it plugs into.

    Known Issue: NL-to-SQL Model Does Not Know About Rill Metrics Views

    Adopted as a spec node — this is the owning record for the Gate 4 gap. Content is the
    original, unedited, except the Resolution section below, which corrects what has since been
    decided. status: draft until the owner reviews it.

    Status

    Open — documented 2026-06-23. Not blocking the current integration
    but must be addressed before the NL-to-SQL layer is considered fully
    integrated with the Rill dashboards.

    Background

    The project instructions (.opencode/instructions.md, Gate 4) state:

    AI agents querying data must use Metrics SQL against metrics views,
    not raw SQL against underlying tables.

    The current NL-to-SQL model was trained on raw DuckDB tables:

    • main_core.dim_students, main_core.fact_attendance, etc.
    • main_analytics.mart_cde_school_accountability
    • main_staging.stg_cde__*

    It does NOT know about Rill metrics views:

    • rill_project/metrics/cde_chronic_absenteeism.yaml
    • rill_project/metrics/cde_suspension.yaml
    • rill_project/metrics/cde_ela.yaml
    • rill_project/metrics/cde_elpac.yaml

    Impact

    The model generates raw DuckDB SQL that bypasses the governed metrics
    layer. This means:

    1. Metric definitions could diverge between the model's SQL and the Rill metrics view definitions.
    2. No row-level security or access control from the metrics layer.
    3. Dashboard and NL-to-SQL results may disagree for the same question.

    Options to Resolve

    1. Prompt engineering only — Add Rill metrics view schemas to the prompt and instruct the model to use Metrics SQL. Low effort, but the model was not trained on Metrics SQL syntax.
    2. Retrain with Metrics SQL pairs — Generate new training pairs that use Metrics SQL against the Rill metrics views. Higher effort, but produces a model that natively speaks the governed layer.
    3. Translation layer — Keep the model generating raw SQL, but add a post-processing step that maps raw SQL to equivalent Metrics SQL. Complex and brittle.

    Recommendation

    Option 2 (retrain) is the right long-term path, but only after the eval
    harness is in place so we can measure the improvement. This should be a
    follow-up plan after the current integration is complete.

    Resolution (decided later, supersedes the options above)

    None of the three options was taken. lfed-app-architecture closes the gap at the
    server instead of at the model: a plane router decides whether a question is answerable
    from a metrics view, and for governed questions the model emits a structured metrics
    query     — view, dimensions, measures, filters, order, limit — whose value sets are the
    view's own metadata, executed by Rill. The model never writes Metrics SQL and never picks
    the plane, so a governed answer cannot drift from the dashboard by construction. Questions
    the router cannot resolve fall to raw marts SQL, visibly marked as ungoverned.

    Two consequences for this record:

    • Retrain toward Metrics SQL is not required for the app, and is no longer the blocking path. It stays lfed-mod-training's option, not the frontend's dependency.
    • The eval harness this document makes a precondition now has a governed-plane mode (lfed-app-observability) that scores governed-versus-marts agreement — which is the measurement Option 2 was waiting for, running without the retrain.

    • .opencode/instructions.md — Gate 4
    • rill_project/metrics/ — the four metrics views the model should learn
    • training/generate_pairs.py — the training data generator (would need a Metrics SQL mode)

    Decision: Option C (raw CDE staging tables for direct query + OBT mart for pre-computed dashboard queries)

    Design Principle

    Option C means two query paths coexist in the warehouse:

    1. Direct query path — CDE staging tables (stg_cde__*) remain available for ad-hoc NL→SQL queries. The model can generate SELECT ... FROM main_cde.stg_cde__suspension when a user asks "What's the suspension rate for Hispanic students in Alameda County?"
    2. Pre-computed path — mart_cde_school_accountability OBT joins all CDE aggregate metrics onto dim_schools at the school × year × reporting_category grain. Dashboard queries hit this single wide table instead of joining 12 staging tables.

    The NL→SQL router (future Phase 5) decides which path to use:

    • Simple lookups → direct staging table query
    • Complex multi-metric comparisons → OBT query (everything pre-joined)

    Grain

    OBT grain: one row per cds_code × academic_year × reporting_category

    This means a school with 15 reporting categories (TA + 7 race groups + 2 gender + 5
    at-risk subgroups) in 4 years = 60 rows in the OBT. The reporting_category = 'TA' (Total
    All Students) rows are the default for school-level dashboards; subgroup rows power equity
    analysis.

    Why this grain and not school × year only:
    CDE reports every metric disaggregated by subgroup. Flattening to school × year would
    either lose the subgroup dimension (unacceptable for equity analysis) or require 100+
    columns (one per subgroup × metric). The school × year × subgroup grain keeps the table
    wide but not absurdly wide.

    Goal

    Local Data Stack (LFED) puts K-12 school-accountability analytics on an ordinary laptop: district SIS exports and California CDE publication files go into DuckDB through dlt and dbt, governed indicators go into Rill metrics views and dashboards, and a person can ask a question in plain language and get a chart — with no cloud service holding student data and no BI tool standing between them and the warehouse.

    Problem

    District accountability questions ("which schools' chronic absenteeism got worse, and how does that line up with EL reclassification?") span CDE downloadable reports and SIS tables that only answer questions the way their publishers designed them to answer. Existing tooling assumes either a cloud warehouse, a fixed dashboard, or a human writing SQL. The data is student-level and re-identifiable, so "upload it and use a hosted assistant" is not an option, and the numbers that count are legally defined indicators with suppression rules — a hand-written query can produce an answer that contradicts the published dashboard.

    Audience

    Today: the project author, working the stack end to end on macOS, plus demonstrations of the surface to educators and researchers. District accountability staff and researchers are the intended end users; no external user has run it yet (unconfirmed from files — this is the stated intent in README.md, not an observed deployment).

    Driving question

    The product bet being tested: can 2–4B-parameter models running on-device carry a generative-UI analytics product — generating the query and authoring the visualization for each answer — without a cloud call or a workstation GPU? The app that tests this is specced in lfed-app-architecture.

    The case study that earlier framed this work is explicitly not the driver. Traces and usage logs remain, as product diagnostics and as the evidence base for the question above — not as study instrumentation.

    Capabilities

    • Ingest. dlt pipelines pull the AeRIES SIS API, import Excel drops, and load CDE pipe-delimited downloadables into Parquet and DuckDB.
    • Model. A dbt project layers staging → core/features/scoring/analytics marts and a privacy-sensitive schema, pseudonymizes student identifiers, and enforces k≥5 suppression inside the models.
    • Govern. A Rill project defines four materialized CDE indicators as metrics views with dimensions, measures, and formats, publishes them as dashboards, and carries pipeline-health alerts.
    • Ask. A local natural-language layer turns a question into SQL using a fine-tuned model, executes it through a read-only guard (allowlisted schemas, blocked privacy tables, SELECT-only, EXPLAIN validation, row cap, watchdog timeout), and returns rows, a summary, generated SQL, and CSV.
    • Evaluate. A gold-SQL eval harness scores a test set against the warehouse; CI runs contract tests over the definition files.
    • Train. Pair generation that executes every candidate query before keeping it, QLoRA adapters on Modal, and a GGUF export path for Apple Silicon.
    • Generate the interface. Specified, not yet built: one local app that answers a question with a visualization the model chose — governed numbers resolved through the metrics views, ungoverned ones through marked warehouse queries. See lfed-app-architecture.

    Requirements

    • Local by construction. No cloud calls, no third-party telemetry, agent endpoints bound to loopback. The stack's whole claim is that the data does not leave the machine.
    • Governed numbers come from the metrics layer. Anything a single CDE indicator view can answer is executed as a structured query against that metrics view, not as free-text SQL against a mart; cross-indicator or student-level questions that cannot be answered by a single metrics view route to the marts layer and are visibly marked. See lfed-docs-known-issues for the gap this rule closes.
    • Ungoverned answers are marked. A warehouse-query answer never looks identical to a governed one: provenance and suppression state are visible in the answer.
    • Small-model budget. Two local models resident inside one app within roughly 8 GB on a 16 GB machine; the product contract names capability and size class, never a checkpoint.
    • One launch. The user runs a single command; the warehouse, the metrics layer, the models, and the browser surface come up without the user configuring endpoints, ports, or weights.
    • No result rows in traces. Trace and usage records capture the question, the generated query, plane, shape, plan acceptance, latency, and rating — not the returned data.

    Non-goals

    • Hosted, multi-tenant, or shared deployments; accounts, login, per-school row-level security, and role management in the app surface. Single local user.
    • Saved boards, pinned answers, sharing, and anything needing a persistence layer — the first build is a transient ask canvas.
    • Packaged .app/.dmg distribution and non-macOS platform parity.
    • Study instrumentation as the reason the app exists: consent tooling, human-review queues, reviewer workflows.
    • Retraining the SQL model or choosing the checkpoints; that is lfed-mod-training's work and the app binds to its contract, not its weights.
    • A published model-accuracy figure. The eval harness measures against a curated question set on the device; nothing here asserts a generalization claim on real district data.

    Responsibility

    Own the server-side request pipeline from a user question to a validated answer envelope streamed over AG-UI (SSE): deterministically route the question to plane=governed or plane=marts, generate the structured metrics_query or guarded SQL, enforce human-in-the-loop (HITL) approval on marts queries, execute the query, invoke the renderer slot for a viz_plan, validate the plan and headline against the payload, attach suppression/provenance caveats, and emit the envelope and row-free trace.

    Request pipeline

    Decisions & rules

    1. Deterministic Plane Router (router.py)

    • At startup, parses rill_project/metrics/*.yaml (cde_chronic_absenteeism, cde_suspension, cde_ela, cde_elpac) and indexes each view's indicator name, title, dimension/measure name, label, description, and curated domain aliases (e.g., "chronic absence", "absenteeism" → cde_chronic_absenteeism; "suspension", "expulsion" → cde_suspension; "ELA", "reading", "distance from standard", "DFS" → cde_ela; "ELPI", "ELPAC", "English learner progress", "reclassification" → cde_elpac).
    • Routing rule:
      • Exactly one governed indicator matched and no student-level / non-CDE dimension requested (e.g. teacher, class section, daily attendance, GPA) → plane = "governed" with metrics_view = <matched_view>.
      • Two or more governed indicators matched (cross-indicator comparison, e.g., chronic absenteeism vs. suspension, which Rill metrics views cannot JOIN) or zero governed indicators matched → plane = "marts" (where main_analytics.mart_cde_school_accountability OBT and main_core.* live).
    • Zero LLM calls in the router: routing latency is < 5 ms and a model cannot choose or spoof plane.

    2. Governed Executor (executors/governed.py)

    • Uses lfed-app-inference with a per-view GBNF grammar constraining output to a metrics_query JSON object:
    • Academic year normalization: Governed CDE views store 4-digit reporting years ('2025'), whereas users often ask for '2024-25' or '2024-2025'. The governed executor normalizes YYYY-YY / YYYY-YYYY filter literals to the 4-digit end year ('2025') before calling Rill.
    • Executes against Rill's local runtime query API and inspects returned rows (and underlying model flags where applicable) for suppressed cells (status_value IS NULL or performance_color = 'No Performance Color'), populating caveats[] with rows_excluded: <int>.

    3. Marts Executor & Guard Hardening (executors/marts.py)

    • Calls nl_query.data_engine rather than re-implementing SQL safety, and closes the execution-time validation gap identified in lfed-mod-nl-query:
      • Before EXPLAIN, validate_sql() must verify that every referenced schema is in get_exposed_schemas(), no referenced table matches _BLOCKED_TABLE_PATTERNS (^_dlt, pii_lookup), and no column in PII_COLUMNS (first_name, last_name, date_of_birth, student_id, ssn, email, phone, address) appears in the query.
    • HITL gate: Streams the validated SQL to the client in a pending state and waits for user action:
      • run: executes as-is.
      • edit: re-runs validate_sql() on the user-edited SQL before executing.
      • reask / cancel: aborts without executing and records status = "aborted" in the trace.
    • Caveat attachment: Always attaches a plane_disclosure caveat (plane=marts), plus either a counted cde_suppression caveat (rows_excluded: <int>) when is_suppressed / is_small_n columns are present, or a policy k_anonymity caveat (rows_excluded: null, message noting groups with n < 5 are omitted upstream by the warehouse) when querying main_core tables.

    4. Viz Plan & Headline Validation (validators.py)

    • Chart validation: Verifies that viz_plan.intent is one of {stat, bar, grouped_bar, line, area, table, comparison}, all referenced columns exist in envelope.columns, and encoding dtypes match the intent (e.g., quantitative measure on y-axis for bar/line/area; stat used only when row_count == 1 or a single aggregate measure is highlighted; line/area permitted only when an ordered time/year dimension such as academic_year is encoded on x). On failure, replaces viz_plan with the deterministic shape classifier output and sets viz_source = "fallback" and fallback_reason.
    • Headline validation: Extracts all numeric tokens from headline and checks that each matches at least one of:
      • any cell value in rows rounded to 0, 1, or 2 decimal places (or ×100 for ratios in [0, 1]),
      • row_count, or
      • a numeric literal present in question or query (e.g., academic year 2025 or 2023-24, grade level, or top-N limit). If headline validation fails while the chart viz_plan is valid, keep the model's viz_plan (viz_source = "model") and replace headline with a deterministic summary ("<Measure Label> by <Dimension Label> (<row_count> rows)"), recording "headline_number_mismatch" in trace diagnostics.

    Boundary

    • Owns no model weights (lfed-app-inference) and no DOM rendering (lfed-app-web).
    • Never persists rows to disk; strips rows before passing the envelope to lfed-app-observability.

    Consumers

    Mounted by lfed-app as the FastAPI AG-UI endpoint; consumed by lfed-app-web over loopback SSE and by lfed-app-observability's on-device eval runner.

    Drivers

    Three constraints pick this design, and they are all product constraints rather than study ones.

    The claim being tested is that a 2–4B model running on the laptop can carry an analytics product: turn a question into a query, and turn the result into the right visualization. That is only a claim if the model is making the decisions, so the app must hand real authorship to the model — and bound the damage it can do.

    Student data makes "call an API" the wrong answer by default, and a district administrator has no way to configure an endpoint, a port, or a weights file. So the whole thing starts with one command and never asks.

    And a number the app prints has to be the number the dashboard prints, which the current client cannot promise (lfed-docs-known-issues). The metrics layer stops being advisory here: it is the governed plane.

    Shape

    The browser is a renderer. Every decision that affects a number — which plane answers, what gets executed, whether a generated plan is trustworthy — is made server-side, where it can be validated and traced.

    Decisions

    CopilotKit as the UI runtime, FastAPI as the agent, no Node runtime. The React provider is pointed straight at the agent with selfManagedAgents — an AG-UI endpoint the app owns and secures itself, which here means bound to loopback with no auth, because the audience is one local user. CopilotKit's TypeScript runtime is the only OSS runtime that works without their cloud "Intelligence" project, and putting a permanently-running second server inside a product whose claim is one transparent local app is the wrong trade. What that gives up, recorded: runtime-side middleware and Intelligence-backed features, and the connection is ours to secure. @ag-ui/client's HttpAgent is the seam; a runtime can be introduced later without touching generation.

    Headless primitives, custom canvas. CopilotKit supplies agent state, tool rendering, and human-in-the-loop; the ask-first canvas is ours. Prebuilt chat components would put the product inside a chatbot shell it is not.

    The rendering model authors the visualization. It sees the executed result plus the view metadata and emits a viz plan — intent, encodings, which measure to headline, what to highlight, the caption. Grammar-locked sampling built from the plan schema and the actual column list means it cannot name a component that does not exist or a column that is not in the result; a server-side validator still checks dtype sanity and that no number in the headline is absent from the payload (matching against payload values rounded to 0–2 decimal places and percentage scaling, row_count, and numeric filter literals). If the chart intent or encodings fail validation, the deterministic shape classifier answers instead with viz_source=fallback visible to the user and the reason traced; if only the headline fails numerical validation while the chart plan is valid, the headline degrades to a deterministic summary without discarding the model's chart plan. A deterministic if/else picking the chart instead would have made the claim untestable: it would prove a lookup table works.

    Seven intents, closed registry. stat, bar, grouped_bar, line, area, table, comparison, plus a caveat block that rides on any of them. A model cannot request a component that isn't registered, so a wrong plan degrades to a table rather than breaking the render. The registry is the auditable boundary of what the app can draw.

    The server routes the plane; governed answers are structured queries, not SQL text. The router resolves a question against metrics-view metadata — view, dimension, measure, aliases. Resolved to a single governed indicator: generate a metrics_query object (view, dimensions, measures, filters, order, limit) whose value sets are that view's own metadata, and let Rill's runtime query API execute it. Unresolved (or spanning tables/indicators outside a single metrics view, such as cross-indicator joins on mart_cde_school_accountability): fall through to the marts guard, and mark the answer. Consequences, accepted deliberately: a 2B model fills a constrained object drawn from one view's real dimensions far more often than it writes correct SQL, governed numbers cannot drift from dashboards by construction, and Rill's runtime metrics query endpoint replaces the broken apis/api.yaml scaffold in lfed-mod-metrics-bi. The model never picks the plane and never writes Metrics SQL, so lfed-docs-known-issues' retrain recommendation is not a dependency of this app.

    Marts answers are gated; governed answers run. plane=marts renders the generated SELECT first and waits for Run / Edit / Re-ask; cancel executes nothing and traces as aborted. Governed answers are aggregate metrics views with suppression already applied upstream, so they stream straight to a chart. The read-only guard makes this a trust decision rather than a safety one, and the friction is spent only where the numbers are ungoverned.

    Grammar-enforced output requires the GGUF backend, so the GGUF backend finally gets built. llama-cpp-python in-process, Metal/CPU auto-selected, one grammar sampler per call (reset between generations), low temperature, bounded max tokens, JSON Schema converted to GBNF. This is the path README.md and ui_strings.py have described for months without existing in code, and it is what makes "in-process" and "grammar-locked" compatible. The transformers/bnb-4bit path stays as a non-grammar fallback and then loses the guarantee — free JSON plus validator, more fallbacks. training/README.md's missing modal_export_gguf.py is the prerequisite for a small GGUF (lfed-mod-training).

    Contract-first model binding. The agent depends on two logical protocols — a SQL/query backend (question, schema → streamed SQL or grammar-locked metrics_query) and a viz backend (result, view_meta → viz plan) — with a sizing requirement attached (resident ≤ 8 GB on a 16 GB machine, first-run download 2–6 GB, < 3 s to first token). Because query generation and viz planning execute sequentially per turn, the two logical slots may be backed by two separate resident GGUF instances or share a single resident 2–4B GGUF instance with per-call grammar/adapter switching. No checkpoint id, LoRA rank, or quantization level appears anywhere in this graph; the retrain runs in parallel in lfed-mod-training and drops in behind the protocol. lfed-mod-nl-query's TransformersLLM-mimicking-llama_cpp seam is the precedent for this.

    Launch is uv run lfed. Resolve or download weights, start Rill and FastAPI as hidden children, wait for health, open the browser, and show a health panel when something failed. No npm step for the user (the SPA bundle is built and vendored), no .app/.dmg, no non-macOS target (lfed-app).

    The app opens with a synthetic district, not the sample. Five-row synthetic Parquet can't produce a chart or trip suppression. Default warehouse: a plausible multi-year district (~15 schools, 3–4 academic years) loaded through the real dlt/dbt path so the schema and k≥5 behavior are identical to production, deterministic so demos and fixtures agree, with the warehouse-resolution chain of lfed-mod-nl-query still pointing at a user's real warehouse when one exists. The owner is supplying the actual synthetic-district dataset; its contents are not yet reviewed here — the requirement is specced, the file is pending input.

    Gradio retires at parity; Rill stops being a UI. The four dashboards are rebuilt natively so browsing and asking share one surface, one design system, and the same suppression disclosure. Rill remains the governed plane's executor and the source of metric definitions — it is hidden as a window, not deleted as a dependency.

    Invariants

    • No egress. No cloud inference, no CopilotKit Intelligence, telemetry disabled in the runtime environment (COPILOTKIT_TELEMETRY_DISABLED=true), and after first-run weight download the request path touches no network.
    • Rows never reach storage. Traces, session logs, and exports record the question, query, plane, intent, viz_source, latency, rating — the envelope's rows field exists only in flight to the browser.
    • Plane is never silent. An ungoverned answer carries a visible provenance mark and a plane=marts record; two answers to the same question with different provenance never look identical.
    • The guard is inherited, not copied. Marts execution calls into nl_query's read-only, allowlisted, EXPLAIN-validated, capped, timed path, so nl_query's guard tests remain the contract for this app.
    • No client-side execution authority. The browser renders envelopes and sends intents; it never holds a connection to the warehouse or the metrics layer.
    • One command, zero configuration. Env overrides exist for development; nothing about a port, endpoint, model path, or weights file is required of the person using it.
    • Suppression is reported, never implied. Both upstream regimes — dbt's dropped k<5 groups and CDE's is_suppressed flag — surface as caveats, because a client cannot recover rows the warehouse discarded.

    Out of scope

    Saved boards, pinning, persistence across launches, and sharing; authentication, per-school row-level security, and multi-tenant or hosted deployment; packaged .app/.dmg and non-macOS builds; consent flows, reviewer queues, and anything else study-shaped; choosing or training the checkpoints; replacing dbt, the marts, or the metrics-view governance itself. Agentic tool-calling chat, MCP surfaces, RAG, and fine-tuning-in-the-loop are all non-goals that the "two model slots, one envelope" design is specifically there to keep out.

    inference — two GGUF slots, grammar-locked planning

    lfed-app-inferencelfed_app/inference/SPEC.md
    parentlfed-app
    childrenleaf node
    depends-onlfed-mod-traininglfed-mod-nl-query
    required bylfed-app-agentlfed-app-build-plan

    Responsibility

    Provide in-process local LLM inference via llama-cpp-python (Metal-accelerated on Apple Silicon, CPU fallback) behind two typed protocols — SQLBackend (question + schema/view metadata → SQL or grammar-locked metrics_query) and VizBackend (executed result summary + column metadata → grammar-locked viz_plan) — within a combined ≤ 8 GB resident memory budget on a 16 GB Mac.

    Slot architecture & residency

    Logical SlotProtocolDefault ResidencyOutput Constraint
    SQL / Query SlotSQLBackendFine-tuned 2–4B Q4_K_M GGUF (LFED_SQL_GGUF_PATH)Free-form ``sql` on plane=marts; dynamic GBNF metrics_query grammar on plane=governed`
    Renderer SlotVizBackendGeneral 2B-class Q4_K_M instruct GGUF (LFED_RENDERER_GGUF_PATH)Dynamic GBNF viz_plan grammar compiled from result columns and the 7-intent registry
    • Two resident GGUFs by default, single-GGUF sharing supported: By default, both GGUF models are loaded at startup so neither turn pays cold-load latency. If LFED_RENDERER_GGUF_PATH equals LFED_SQL_GGUF_PATH (or on memory-constrained machines), both protocols bind to the same underlying llama_cpp.Llama instance with per-call LlamaGrammar reset.
    • Concurrency & thread safety: Because llama_cpp.Llama contexts are not thread-safe for concurrent decoding, an asyncio.Lock guards each physical Llama instance. Within a single user turn, SQLBackend and VizBackend execute strictly sequentially.

    Memory & latency budget

    • Combined resident footprint: ≤ 8 GB RSS across both Llama instances (e.g., ~2.6 GB for a 4B Q4_K_M SQL model + ~1.5 GB for a 2B Q4_K_M Renderer model + bounded KV caches with n_ctx=4096, n_gpu_layers=-1 on Metal).
    • Generation bounds:
      • SQLBackend: temperature=0.0, max_tokens=512, time-to-first-token < 3 s.
      • VizBackend: temperature=0.1, max_tokens=384, fresh LlamaGrammar compiled per call from the actual column names and dtypes returned by the query.

    Dynamic GBNF grammar construction (grammars.py)

    1. build_metrics_query_grammar(view_meta):
      • Constrains metrics_view to the literal view name, dimensions to a non-empty subset of view_meta.dimension_names, measures to a non-empty subset of view_meta.measure_names, where[].column to valid dimension names, sort[].column to selected dimensions/measures, and limit to 1..1000.
      • Guarantees the governed query generator cannot invent a column, measure, or syntax error.
    2. build_viz_plan_grammar(columns, row_count):
      • Constrains intent to "stat" | "bar" | "grouped_bar" | "line" | "area" | "table" | "comparison".
      • Constrains encodings.x, encodings.y, encodings.series, and highlight.column to the exact column names present in columns[].
      • Constrains headline and caption to bounded single-line JSON strings.
      • Compiled via llama_cpp.LlamaGrammar.from_json_schema(json.dumps(schema)) on a fresh sampler per invocation so grammar state never leaks across turns.

    Fallback backend

    • Retains nl_query.model_inference.TransformersLLM as an opt-in fallback (LFED_INFERENCE_BACKEND=transformers) for developer environments without llama-cpp-python wheels. When running on the transformers fallback, GBNF sampling is unavailable and the agent relies on JSON extraction + server-side validation (lfed-app-agent).

    Boundary

    • Exposes only the SQLBackend and VizBackend Python protocols and grammar builders; knows nothing about FastAPI, SSE, DuckDB connections, or Rill HTTP APIs.
    • Never hardcodes a Hugging Face checkpoint ID inside lfed-app-agent; default model filenames/repos live solely in lfed_app/config.py.

    Consumers

    Initialized at startup by lfed-app and called per turn by lfed-app-agent and lfed-app-observability (eval runner).

    On-device evaluation harness (eval_governed.py)

    Extends nl_query/eval.py (lfed-mod-nl-query) with three evaluation modes over the deterministic synthetic district warehouse:

    Responsibility

    Let a person ask a question in plain language and get warehouse rows back, without ever letting a model write to the database or see a re-identification key. Flat package, no subpackages: app.py (Gradio UI), data_engine.py (connection + guard), model_inference.py (backend), prompts.py (context), ui_strings.py (copy), eval.py (harness), tests/.

    The guard in data_engine.py is the artifact this module is really for; the Gradio surface is scaffolding around it and is superseded by lfed-app-architecture.

    The guard, as built

    • EXPLAIN is the real validator. Forbidden tokens catch intent; EXPLAIN catches invented columns and tables, and it is schema-aware because the connection is live.
    • Introspection filtering vs. execution validation gap. DEFAULT_EXPOSED_SCHEMAS, _BLOCKED_TABLE_PATTERNS, and PII_COLUMNS filter what get_schema_info() shows the prompt, but validate_sql() does not check them at execution time — it only checks FORBIDDEN_TOKENS, SELECT, BLOCKED_SCHEMAS / _BLOCKED_SCHEMA_PATTERNS, and EXPLAIN. Before lfed-app-architecture allows human-in-the-loop SQL editing on plane=marts, validate_sql() must enforce the schema allowlist, blocked table patterns, and PII column exclusions at execution time too.
    • app.py overrides the 10-second default to 30 seconds at execution (app.py:221). Anything that inherits execute_safe gets 10 s unless it passes its own timeout — a discrepancy the app layer must decide about deliberately rather than inherit by accident.
    • get_schema_info() introspects live, dropping blocked/unexposed schemas, _dlt* and pii tables, and PII columns; the static DEFAULT_SCHEMA in prompts.py:66-223 is used only when introspection fails.

    Known drift

    • prompts.py advertises main_staging.stg_cde__* in its static DEFAULT_SCHEMA and its system prompt instructs the model to use CDE staging tables, but main_staging is not in DEFAULT_EXPOSED_SCHEMAS. When live introspection succeeds, get_schema_info() hides main_staging from the schema block while the system prompt still tells the model to query main_staging.stg_cde__* (and because validate_sql() does not enforce DEFAULT_EXPOSED_SCHEMAS, those queries still execute if the model guesses the column names). Either DEFAULT_EXPOSED_SCHEMAS needs main_staging or prompts.py should stop offering staging tables. Unconfirmed; lfed-docs-phase4a expected staging to be visible.
    • academic_year has three distinct string formats across the stack: 'YYYY' (e.g. '2025') in the governed rill_cde_* views, 'YYYY-YY' (e.g. '2023-24') in mart_cde_school_accountability and stg_cde__*, and 'YYYY-YYYY' (e.g. '2023-2024') in Aeries main_core tables. Any router or prompt context must keep these distinct per target table.
    • The metrics views the governed plane is made of appear nowhere in the prompt or schema context — the substance of lfed-docs-known-issues.
    • model_inference.py is transformers + PEFT only (base unsloth/qwen2.5-coder-14b-instruct-bnb-4bit, adapter resolved from LFED_ADAPTER_REPO → models/lora-warehouse-r64/ → HF id). The header says the llama.cpp backend was removed because it could not reach ZeroGPU's PyTorch-only CUDA emulation, yet llama-cpp-python is still declared in the nl-query extra and ui_strings.py:120 tells users a GGUF/llama.cpp option exists. Documented capability, absent implementation.
    • No suppression reporting at answer time: k≥5 is applied upstream in dbt (lfed-mod-data-framework) and CDE's own is_suppressed flag is a column, so a Gradio answer can present a group that was silently dropped.

    Boundary

    • Never imports oss_framework/; meets the warehouse as a DuckDB file.
    • Opens every connection read-only. create_session() hard-codes it.
    • Retires when lfed-app-architecture reaches parity; until then it stays the reference surface and its guard tests stay the contract for anything that executes generated SQL (tests/test_execution_guard.py, test_data_engine.py, test_gradio_e2e.py, test_model_inference.py, test_eval_harness.py).

    Consumers

    lfed-mod-training seeds its prompt context from prompts.py. lfed-app-architecture inherits this module's guard and eval harness rather than reimplementing either.
